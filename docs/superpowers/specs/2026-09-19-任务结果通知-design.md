# 任务结果通知 设计

日期：2026-09-19
状态：已批准

## 背景

日常任务执行完只有四行 console 摘要（[daily.ts:518-523](../../../src/model/daily.ts#L518-L523)）：成功/跳过/失败/总计。脚本常与「执行完息屏」配合在无人看管下运行，跑完人不在手机旁；AutoX.js 控制台日志在进程重启后也不可回溯。结果是"跑了没有、哪几项没做成"这件事没有可及的入口。

设置页的「执行结果通知」开关（[layout.xml:105](../../../layout/layout.xml#L105)）自加入起是占位，标注"功能待实现，暂无代码读取该开关"。

## 目标

1. 屏幕右上角常驻计数条，实时显示本轮 成功/跳过/异常 条数
2. 整轮跑完发一条系统通知：标题带汇总数字，展开态列出跳过与异常的任务及原因
3. 顺带修正两处会让"条数"算错的既有缺陷

**不做**：不覆盖兑换码/探索/获取队友信息三个入口；不做网络推送（webhook）；不做跨运行的历史归档与持久化统计。

## 设计

### 1. 架构

三层单向依赖。`daily.ts` 只发事件、不认识任何人怎么展示：

```
daily.ts  doTask()
    │  发布任务事件
    ▼
src/utils/taskBus.ts        事件类型定义 + 订阅/发布/清空        纯逻辑，零状态
    │  通知订阅者
    ├──────────────────────────────┐
    ▼                              ▼
src/utils/taskReport.ts      src/utils/taskNotifier.ts
累加本轮计数与明细             渲染层：右上角计数条 + 结束时发 notice
导出汇总快照 + 纯格式化函数         │
（无 UI，可单测）                   └── 读取汇总 ──> taskReport（单向，不回写）
```

`taskReport` 与 `taskNotifier` 互不相识，只共享 `taskBus` 的事件契约和 `taskReport` 导出的汇总类型。

**`daily.ts` 的 import 面被压到两个符号**：`发布`（发事件）和 `初始化通知`（一次装配）。它不知道汇总怎么算、文案怎么拼、窗口怎么建——方案 C 的价值（加订阅者不动 `daily.ts`）由此保住。`初始化通知` 是唯一的例外，因为开关要从 UI 读、而 UI 只有 `daily.ts` 认得，这个参数必须从外面传进去。

**关键取舍：发布是同步的。** 订阅者只做数组 push 和字符串拼接，同步执行最直观，出错时堆栈直接指向 `doTask`。同步还消除了一个真实竞态——`taskNotifier` 在收到「整轮结束」时读 `taskReport.本轮汇总()`，因为「任务结束」事件是一个个同步发布的，此时所有累加都已完成。

**代价：订阅者异常不隔离。** 任一订阅者抛异常会冒泡进 `doTask` 的 catch，被误判成任务失败。所以两个订阅者的处理函数内部各自 `try/catch` 兜底，异常只 `console.log`，不向外抛。

### 2. `src/utils/taskBus.ts` — 事件契约

```ts
/** 单个任务结束时发布 */
export interface 任务结束事件 {
  类型: '任务结束'
  名: string                              // doTask 的 label
  状态: '成功' | '跳过' | '异常'
  原因?: string                           // 跳过/异常的原因；成功时无
  耗时: number                            // 秒，一位小数
  服?: string                             // 当前区服（多账号模式用于定位）
}
/** runDaily 开始时发布，订阅者据此清零 / 重置 UI */
export interface 本轮开始事件 {
  类型: '本轮开始'
}
/** runDaily 结束时发布（正常返回或异常中断都会发） */
export interface 整轮结束事件 {
  类型: '整轮结束'
  结果: '完成' | '已停止'
}
export type 任务事件 = 任务结束事件 | 本轮开始事件 | 整轮结束事件

export function 订阅(fn: (e: 任务事件) => void): void
export function 发布(e: 任务事件): void
export function 清空订阅(): void           // 供诊断脚本复位用
```

订阅按注册顺序同步调用，不提供取消订阅（本轮用完即弃，`清空订阅` 足够）。

### 3. `src/utils/taskReport.ts` — 汇总与文案

订阅 `taskBus`，维护本轮状态；文件顶部完成订阅注册。

```ts
export interface 明细项 { 状态: '跳过' | '异常'; 名: string; 原因: string; 服?: string }
export interface 汇总结果 {
  成功: number
  跳过: number
  异常: number
  条数: number          // 恒等于 成功 + 跳过 + 异常；通知正文里显示为「合计」
  明细: 明细项[]        // 跳过与异常，按发生顺序
}

export function 本轮汇总(): 汇总结果   // 名字与接口「汇总结果」区分开，避免类型/值同名
export function 重置本轮(): void
```

四个格式化函数（纯函数，无副作用，是单测的主要目标）：

| 函数 | 输出 | 用途 |
|---|---|---|
| `格式化计数条(汇总)` | `✅ 12  ⏭ 3  ❌ 2` | 悬浮条文字 |
| `格式化通知标题(汇总, 结果)` | `日常完成 ✅12 ⏭3 ❌2` / `日常已停止 ✅5 ⏭1 ❌0` | 通知标题 |
| `格式化通知正文(汇总)` | `成功 12 \| 跳过 3 \| 异常 2 \| 合计 17` | 通知折叠态 |
| `格式化通知明细(汇总)` | 分节列明细，见下 | 通知 bigContent |

`格式化通知明细` 的输出格式（明细为空时返回空串，调用方据此决定是否传 `bigContent`）：

```
跳过 3 项
· 观影便利店 免费 — 未找到入口
· [S123] 军团 每日一刀 — 未找到入口
异常 2 项
· 闪退19次 — NavigationError: xxx
```

- 带 `服` 的明细项渲染成 `[服务器名] 任务名`，多服模式下才能定位是哪台服
- **跳过/异常各超过 5 条只列前 5**，节尾补 `… 其余 N 项见运行日志`
- `原因` 为空时渲染 `— 未知原因`（异常事件可能没有 message）

### 4. `src/utils/taskNotifier.ts` — 渲染层

对外只暴露一个装配入口：

```ts
/** 订阅只注册一次；每次调用按传入值刷新启用状态（重复调用不会重复订阅） */
export function 初始化通知(启用: boolean): void
```

收到 `/本轮开始/` 时若 `启用` 为 true 则创建或复用计数条窗口并清空文字，否则跳过；收到 `/任务结束/` 刷新计数条文字；收到 `/整轮结束/` 发通知。开关关闭时三个分支全部短路——**不建窗、不发通知，也不影响 `taskReport` 继续计数**（将来加别的订阅者不受影响）。

**计数条**

新增 [layout/status.xml](../../../layout/status.xml)，属性照抄 [small.xml](../../../layout/small.xml) 里已验证的写法：

```xml
<text id="计数" w="150" h="30" alpha="0.8" padding="0" margin="0">✅ 0  ⏭ 0  ❌ 0</text>
```

用 `<text>`（[JsTextView](../../../declarations/autojs6/aj6-int-init.d.ts#L1356)）而非 `<button>`：只读展示，不该有点击语义。

- 新类 `StatusWindow extends FloatWindow<{ 计数: View & JsTextView }>`，**模块单例**——重复启动不会叠加出多个窗口
- 位置 `device.width - 150, 60`，正好在现有小球（[SmallWindows.ts:7](../../../src/SmallWindows.ts#L7) 的 `device.width - 150, 20`，高 36）正下方
- 复用 `FloatWindow.draggable()` 允许拖开避让
- **不复用也不碰 [smallWindow](../../../src/SmallWindows.ts#L46)**：它的 `close()` 里有 `threads.shutDownAll()`，共用会误杀任务线程
- 所有 UI 操作走 `ui.run`——`doTask` 跑在子线程（[main.ts:190](../../../src/main.ts#L190)）
- 收到 `/整轮结束/` 后**保留在屏上**显示最终计数，不 hide；下次运行由 `/本轮开始/` 复用它并重置文字

**通知**

```ts
// AutoJs6 文档: notice(title, content, options) / notice.isEnabled / notice.ensureEnabled
// 声明: declarations/autojs6/aj6-int-notice.d.ts:16, 源 %AutoJs6Assets%/modules/__notice__.js
if (!notice.isEnabled()) {
  try { notice.ensureEnabled() } catch (e) { /* 引导失败不阻塞, 走下面的降级分支 */ }
}
try {
  notice(标题, 正文, {
    bigContent: 明细,
    notificationId: 1919,     // 固定值 → 覆盖上一条, 通知栏不堆积
    autoCancel: true,
    priority: 'default',      // 带提示音, 跑完锁屏也能听到
  })
} catch (e) {
  console.log('[通知] 发送失败: ' + (e.message || e))
  // 降级: 结果仍进日志与详细日志文件
  console.log(格式化通知标题(汇总, 结果) + ' | ' + 格式化通知正文(汇总))
  toast('通知权限未开启，结果见运行日志')
}
```

固定 `notificationId` 让本次覆盖上次，避免每次运行留一条。取 1919 是随手选的不占号段的值，是否与 AutoJs6 自身或其它脚本的通知撞车待真机确认（见「待真机确认」第 4 条）。

### 5. `src/model/daily.ts` — 埋点与生命周期

**删除** [daily.ts:62-65](../../../src/model/daily.ts#L62-L65) 的四个模块级计数器。总条数不再手工维护，而是"report 收到几个「任务结束」事件就是几条"——[daily.ts:522](../../../src/model/daily.ts#L522) 那种"总计 ≠ 三项之和"从结构上不再可能发生。

`doTask` 改造（新增可选第三参，默认 `true`，现有 26 个调用点一行不改）：

```ts
function doTask(label: string, action: () => boolean, 配置?: { 计数?: boolean }): boolean {
  var 要计数 = !配置 || 配置.计数 !== false
  ...
  // 三态分支里原本的 successTasks++ / skipTasks++ / failTasks++ 全部换成:
  if (要计数) 发布({ 类型: '任务结束', 名: label, 状态: '成功', 耗时: elapsed, 服: currentServer || undefined })
  ...
}
```

`/计数: false` 时仍保留 try/catch 与全部日志，只是不发事件。

**三处裸 `failTasks++`** 改为发布异常事件，各自带上明确任务名：

| 位置 | 事件名 |
|---|---|
| [daily.ts:438](../../../src/model/daily.ts#L438) | `战斗页活动批量 — 无法进入战斗页` |
| [daily.ts:467](../../../src/model/daily.ts#L467) | `{目标.名} — 入口点击后未进入页面` |
| [daily.ts:474](../../../src/model/daily.ts#L474) | `战斗页活动批量 — 无法返回战斗页` |

**观影签到去重**（[daily.ts:407-424](../../../src/model/daily.ts#L407-L424)）：该条目的 `执行` 只是串接两个子 `doTask`（签到、便利店），自身无独立动作，却让 2 个开关被计成 3 条。规则是「**`doTask` 的 action 若只是串接其它 `doTask`、自身无独立动作，则不计数**」，故 [daily.ts:409](../../../src/model/daily.ts#L409) 传 `{ 计数: false }`，由两个子任务各自计数。

同一规则下 [daily.ts:279](../../../src/model/daily.ts#L279) 的 `军团` **保留计数**：它自己做了 `nav(军团)` 导航动作，且"军团页进不去"正是需要在通知里看到的异常。

`runDaily` 生命周期：

```ts
export function runDaily(): void {
  初始化通知(isDailyEnabled('执行结果通知'))   // 开关在此读一次
  发布({ 类型: '本轮开始' })
  var 正常结束 = false
  try {
    ...现有执行逻辑（含多服循环）不变...
    正常结束 = true
  } finally {
    发布({ 类型: '整轮结束', 结果: 正常结束 ? '完成' : '已停止' })
  }
}
```

`finally` 保证手动停止时也发通知。实测上能逃出 `runDaily` 的异常几乎只有 `isStopException`——其余异常都被 `doTask` 和 `nav` 接住了——所以「已停止」这个措辞是准确的。

**末尾的 console 摘要整段删除。** [daily.ts:518-523](../../../src/model/daily.ts#L518-L523) 依赖那四个被删掉的计数器，改由 `taskReport` 在收到「整轮结束」时输出：

```
================================
   日常任务 — 完成
   成功: 12 | 跳过: 3 | 异常: 2 | 合计: 17
================================
```

文案里的「失败」一并改成「异常」，与计数条、通知栏用词统一。放 `taskReport` 而不是 `taskNotifier` 的原因：它是纯文本、不依赖 floaty，诊断脚本在无 UI 环境下也要能看到这段输出；而且详细日志开关会把它一起写进文件，正是需要留档的内容。

## 已知限制

1. 计数条无点击交互，不可清零、不可手动隐藏（只能拖动避让）
2. 无跨运行历史：脚本重跑后上一轮数字不留档，只有详细日志文件里有文字记录
3. 多服模式下计数条是**跨服累计**，不区分单服
4. `taskReport` 与 `taskNotifier` 的订阅在模块加载时注册一次，`清空订阅` 后不会自动恢复——只有诊断脚本会用到，正常运行路径不碰

## 待真机确认

实现前无法从代码确定的项，实现后逐条实测：

1. `<text>` 的 `w`/`h`/`alpha`/`padding`/`margin` 这套自定义属性在 floaty 下是否与 `<button>` 一致（small.xml 验证过的是 button，text 未验证）
2. 透明背景下计数文字在游戏亮色 UI 上是否看得清，必要时补半透明背景（属性名以设备实测为准）
3. 脚本结束、以及小球「停止」（[SmallWindows.ts:23](../../../src/SmallWindows.ts#L23) 的 `threads.shutDownAll()`）之后，计数条是否残留或自动回收
4. 固定 `notificationId: 1919` 是否与 AutoJs6 自身或其它脚本的通知互相覆盖
5. 计数条 `w="150"` 在三位数（如 `✅ 100  ⏭ 50  ❌ 20`）时是否放得下，放不下就加宽或省略成 `✅100 ⏭50 ❌20`
6. `notice.ensureEnabled()` 的实际表现——是否弹系统授权框、用户拒绝后 `isEnabled()` 是否仍为 false
7. 多服模式下 `currentServer` 的赋值时机与事件发布时机是否对齐，`服` 字段有无错配或缺失

## 测试

项目未安装 jest/mocha（[package.json:12-22](../../../package.json#L12-L22) 只有构建工具），既有测试范式是"加 webpack entry → dist 脚本 → 真机运行"。本设计沿用该范式。

新增 `test/任务通知诊断.ts`，并在 [webpack.config.js:6-13](../../../webpack.config.js#L6-L13) 的 `entry` 加一行。真实调用 `taskBus` / `taskReport` 的函数并断言（不写 `1===1` 式废话断言）。用例之间用 `发布({ 类型: '本轮开始' })` 清场，不需要 `清空订阅`：

**正常**
- 依次发布 成功×2、跳过×1、异常×1 → 断言 `成功/跳过/异常` 分别为 2/1/1，且 `条数 === 4`
- 断言 `格式化通知正文` 输出 `成功 2 | 跳过 1 | 异常 1 | 合计 4`

**空**
- 只发「本轮开始」不发任何任务事件 → 四个计数全 0，`格式化通知明细` 返回空串，标题不抛异常

**异常**
- 异常事件不带 `原因` → 断言明细行含 `— 未知原因`，且不出现 `undefined`
- 跳过事件带 `服` → 断言渲染成 `[S123] 任务名`

**边界**
- 跳过正好 5 条 → 全部列出，不含省略号
- 跳过 6 条 → 只列 5 条，尾行为 `… 其余 1 项见运行日志`
- 同名任务连发 3 次 → 断言计 3 条（对应"执行次数 = 条数"的语义）

**渲染冒烟**（真机，无法断言，人眼确认）
- 建计数条 → 连发 3 个事件 → 看数字逐个跳动
- 发一条带 `bigContent` 的通知 → 下拉展开看明细是否完整

**回归影响**：改动前先开着详细日志完整跑一轮、留存日志；改动后再跑一轮（"全部账号"关闭与打开各一次），两轮比对。**预期差异只应有两处**——观影签到从 3 条降到 2 条；三处裸计数现在计入合计，所以合计会比旧版大。除此之外每类任务的条数应当逐一对得上，若还有出入就是 `doTask` 埋点漏了地方。
