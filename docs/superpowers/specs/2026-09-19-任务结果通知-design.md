# 任务结果通知 设计

日期：2026-09-19
状态：已批准

## 背景

日常任务执行完只有四行 console 摘要（[daily.ts:518-523](../../../src/model/daily.ts#L518-L523)）：成功/跳过/失败/总计。脚本常与「执行完息屏」配合在无人看管下运行，跑完人不在手机旁；AutoX.js 控制台日志在进程重启后也不可回溯。结果是"跑了没有、哪几项没做成"这件事没有可及的入口。

设置页的「执行结果通知」开关（[layout.xml:105](../../../layout/layout.xml#L105)）自加入起是占位，标注"功能待实现，暂无代码读取该开关"。

## 目标

1. 屏幕右上角常驻计数条，实时显示本轮 成功/跳过/异常 条数
2. 整轮跑完发一条系统通知：标题带汇总数字，展开态列出跳过与异常的任务及原因
3. 顺带修正两处会让"条数"算错的既有缺陷

**不做**：不覆盖兑换码/探索/获取队友信息三个入口；不做网络推送（webhook）；不做跨运行的历史归档与持久化统计。

## 设计

### 1. 架构

三层单向依赖。`daily.ts` 只发事件、不认识任何人怎么展示：

```
daily.ts  doTask()
    │  发布任务事件
    ▼
src/utils/taskBus.ts        事件类型定义 + 订阅/发布/清空        纯逻辑，零状态
    │  通知订阅者
    ├──────────────────────────────┐
    ▼                              ▼
src/utils/taskReport.ts      src/utils/taskNotifier.ts
累加本轮计数与明细             渲染层：右上角计数条 + 结束时发系统通知
导出汇总快照 + 纯格式化函数         │
（无 UI，可单测）                   └── 读取汇总 ──> taskReport（单向，不回写）
```

`taskReport` 与 `taskNotifier` 互不相识，只共享 `taskBus` 的事件契约和 `taskReport` 导出的汇总类型。

**`daily.ts` 的 import 面被压到两个符号**：`发布`（发事件）和 `初始化通知`（一次装配）。它不知道汇总怎么算、文案怎么拼、窗口怎么建——方案 C 的价值（加订阅者不动 `daily.ts`）由此保住。`初始化通知` 是唯一的例外，因为开关要从 UI 读、而 UI 只有 `daily.ts` 认得，这个参数必须从外面传进去。

**关键取舍：发布是同步的。** 订阅者只做数组 push 和字符串拼接，同步执行最直观，出错时堆栈直接指向 `doTask`。同步还消除了一个真实竞态——`taskNotifier` 在收到「整轮结束」时读 `taskReport.本轮汇总()`，因为「任务结束」事件是一个个同步发布的，此时所有累加都已完成。

**代价：订阅者异常不隔离。** 任一订阅者抛异常会冒泡进 `doTask` 的 catch，被误判成任务失败。所以两个订阅者的处理函数内部各自 `try/catch` 兜底，异常只 `console.log`，不向外抛。

### 2. `src/utils/taskBus.ts` — 事件契约

```ts
/** 单个任务结束时发布 */
export interface 任务结束事件 {
  类型: '任务结束'
  名: string                              // doTask 的 label
  状态: '成功' | '跳过' | '异常'
  原因?: string                           // 跳过/异常的原因；成功时无
  耗时: number                            // 秒，一位小数
  服?: string                             // 当前区服（多账号模式用于定位）
}
/** runDaily 开始时发布，订阅者据此清零 / 重置 UI */
export interface 本轮开始事件 {
  类型: '本轮开始'
}
/** runDaily 结束时发布（正常返回或异常中断都会发） */
export interface 整轮结束事件 {
  类型: '整轮结束'
  结果: '完成' | '已停止'
}
export type 任务事件 = 任务结束事件 | 本轮开始事件 | 整轮结束事件

export function 订阅(fn: (e: 任务事件) => void): void
export function 发布(e: 任务事件): void
export function 订阅(fn: (e: 任务事件) => void): () => void   // 返回取消订阅函数
```

> **规格修订（2026-09-19，代码质量审查发现）**：原设计只有 `订阅` / `发布` / `清空订阅`，且明确「不提供取消订阅」。这在实现任务 2 时会引爆：`taskReport` 在**模块体**里注册订阅，而 webpack 把模块体排在入口脚本体之前，诊断脚本一调 `清空订阅()` 就会把 `taskReport` 的订阅一并抹掉，导致后续全部计数断言假失败。
>
> 改为 `订阅` 返回取消句柄、**删除 `清空订阅`**：诊断脚本只摘掉自己注册的监听器，不触碰全局状态；任务 4/5 再加订阅者也不会互相干扰。

订阅按注册顺序同步调用。取消订阅用 `订阅` 返回的句柄，不做全局清空——`taskReport` / `taskNotifier` 的订阅在模块加载时注册，全局清空会把它们一起抹掉。

### 3. `src/utils/taskReport.ts` — 汇总与文案

订阅 `taskBus`，维护本轮状态；文件顶部完成订阅注册。

```ts
export interface 明细项 { 状态: '跳过' | '异常'; 名: string; 原因: string; 服?: string }
export interface 汇总结果 {
  成功: number
  跳过: number
  异常: number
  条数: number          // 恒等于 成功 + 跳过 + 异常；通知正文里显示为「合计」
  明细: 明细项[]        // 跳过与异常，按发生顺序
}

export function 本轮汇总(): 汇总结果   // 名字与接口「汇总结果」区分开，避免类型/值同名
export function 重置本轮(): void
```

四个格式化函数（纯函数，无副作用，是单测的主要目标）：

| 函数 | 输出 | 用途 |
|---|---|---|
| `格式化计数条(汇总)` | `✅ 12  ⏭ 3  ❌ 2` | 悬浮条文字 |
| `格式化通知标题(汇总, 结果)` | `日常完成 ✅12 ⏭3 ❌2` / `日常已停止 ✅5 ⏭1 ❌0` | 通知标题 |
| `格式化通知正文(汇总)` | `成功 12 \| 跳过 3 \| 异常 2 \| 合计 17` | 通知折叠态 |
| `格式化通知明细(汇总)` | 分节列明细，见下 | 通知 bigContent |

`格式化通知明细` 的输出格式（明细为空时返回空串，调用方据此决定是否设置 `BigTextStyle`）：

```
跳过 3 项
· 观影便利店 免费 — 未找到入口
· [S123] 军团 每日一刀 — 未找到入口
异常 2 项
· 闪退19次 — NavigationError: xxx
```

- 带 `服` 的明细项渲染成 `[服务器名] 任务名`，多服模式下才能定位是哪台服
- **跳过/异常各超过 5 条只列前 5**，节尾补 `… 其余 N 项见运行日志`
- `原因` 为空时渲染 `— 未知原因`（异常事件可能没有 message）

> **跳过原因的来源（2026-09-19 补充）**：`doTask` 原先只拿到 `action()` 的布尔返回值，跳过原因无从得知，明细里会清一色显示「未知原因」——而明细存在的意义就是回答"为什么没做成"。为此把动作的返回值放宽成联合类型（见 §5），并统一两条规则：
> - `action()` 返回 `false` → 原因记 `未完成`（动作跑了，但页面上没有可领的东西）
> - `nav()` 失败 → 原因记 `导航失败`（页面根本没进去）
>
> 这两个原因刻意**不重复任务名里已有的页名**（明细行本身就写着 `军团 每日一刀`），只回答"卡在哪一类"。更细的原因（如"今日已领""未找到入口"）留给将来在具体调用点用 `{ ok: false, 原因: '...' }` 显式提供。

### 4. `src/utils/taskNotifier.ts` — 渲染层

对外只暴露一个装配入口：

```ts
/** 订阅只注册一次；每次调用按传入值刷新启用状态（重复调用不会重复订阅） */
export function 初始化通知(启用: boolean): void
```

收到 `/本轮开始/` 时若 `启用` 为 true 则创建或复用计数条窗口并清空文字，否则跳过；收到 `/任务结束/` 刷新计数条文字；收到 `/整轮结束/` 发通知。开关关闭时三个分支全部短路——**不建窗、不发通知，也不影响 `taskReport` 继续计数**（将来加别的订阅者不受影响）。

> **开关关闭时还要撤掉已存在的窗口（2026-09-19 代码质量审查补充）**：上面的"短路"只保证不**新建**窗，但上一轮留下的计数条会带着旧数字僵在屏上——用户在设置页取消勾选后重新启动，屏上仍挂着上一轮的 ✅/❌。所以 `初始化通知(false)` 必须同时隐藏已有窗口。相应地，文件头"开关关闭时全部短路"要写成"关闭时不建窗并隐藏已有窗"。

**计数条**

新增 [layout/status.xml](../../../layout/status.xml)，属性照抄 [small.xml](../../../layout/small.xml) 里已验证的写法：

```xml
<text id="计数" w="150" h="30" bg="#E6000000" textColor="#FFFFFF" padding="0" margin="0">✅ 0  ⏭ 0  ❌ 0</text>
```

> **真机验收修订（2026-09-19，k 实测）**：原设计是 `alpha="0.8"` 的裸文字，k 反馈「透明度太高看不清」——`alpha` 是整视图透明度，调高只会让它在亮背景上更糊。改为**深色半透明底 + 白字**：设备实测 `bg` 与 `textColor` 在 floaty `<text>` 上均生效（`getBackground()` 返回 `ColorDrawable`、`getCurrentTextColor()` 返回 `-1`）。

用 `<text>`（[JsTextView](../../../declarations/autojs6/aj6-int-init.d.ts#L1356)）而非 `<button>`：只读展示，不该有点击语义。

- 新类 `StatusWindow extends FloatWindow<{ 计数: View & JsTextView }>`，**模块单例**——重复启动不会叠加出多个窗口
- 位置：右边缘贴屏幕右边，纵向 60（在小球下方）。**必须按 density 换算**：`device.width - Math.round(计数条宽dp * density)`，不能直接写 `device.width - 150`

> **真机验收修订（2026-09-19，k 实测「标签右边一部分在屏幕外」）**：`floaty` 布局的 `w` 单位是 **dp**，而 `setPosition` 收的是 **px**——同一个 `150` 在两处含义不同。实测（1080px / density 2.625）：`w="150"` 实际宽 **394px**，而 `device.width - 150` 把左边缘放在 930px，于是右边缘到 1324px，**超出屏幕 244px**。改成按 density 换算后右边缘正好落在 1080。注意现有小球（[SmallWindows.ts:7](../../../src/SmallWindows.ts#L7)）有同样的隐患，只是它的 `w="50"` 只有 131px，偏内 19px 看不出来，**本次不动它**。
- **不接收触摸（`FLAG_NOT_TOUCHABLE`），因此也就不用 `draggable()`**：k 实测反馈「把计数条拖到小球上会遮挡小球，点击触发不了」——小球是运行中唯一的「停止」入口，被挡住等于停不下来。计数条是只读 HUD，让它点击穿透是唯一能保证它永不挡操作的做法。代价是位置固定（`device.width - 150, 60`），要挪就改这个常量。设置 flag 的反射写法同 [FloatWindow.ts:67-92](../../../component/FloatWindow.ts#L67-L92)；**`updateWindowLayoutParams` 必须在 `ui.run` 里调**，实测直接调会抛 `CalledFromWrongThreadException`
- **不复用也不碰 [smallWindow](../../../src/SmallWindows.ts#L46)**：它的 `close()` 里有 `threads.shutDownAll()`，共用会误杀任务线程
- **所有 UI 操作走 `ui.run`，建窗也算**（2026-09-19 代码质量审查补充）：`doTask` 跑在子线程（[main.ts:190](../../../src/main.ts#L190)），生产上首次事件就会在子线程触发。`ui.run` 必须包住 `new 计数条窗口()` 这一整段（含 `setPosition` 与构造里的反射调用），而不只是 `setText`——规格的实测结论是"**在 `ui.run` 回调里**建窗可用"，子线程直接建窗未被验证。做法是把 `ui.run` 上提到 `刷新计数条`，窗口类内部的 `ui.run` 随之取消
- 不设"是否已显示"标志：`setVisibility(0)` 在 flag 未变时是空操作，加标志反而引入"将来新增隐藏路径必须复位它，否则窗口再也显示不出来"的隐含约束
- 收到 `/整轮结束/` 后**保留在屏上**显示最终计数，不 hide；下次运行由 `/本轮开始/` 复用它并重置文字（**开关关闭时例外，见上**）
- 位置里的 `150` 与布局的 `w="150"` 是同一个数字的两份拷贝，改宽度时要同步改位置——`small.xml` 那边没有这个耦合，是本次新引入的

**通知**

> **规格修订（2026-09-19，真机实测）**：本节原设计基于 AutoJs6 的 `notice()` API，该 API **在设备上不存在**。设备运行时是 AutoX.js v6.6.7（Auto.js 4.1.1 血统），实测 `notice` 未定义；AutoX.js 的 `notifications()` 是「拉出通知栏」的按键模拟函数而非发送通知；`notification` 模块属 Auto.js Pro 9，开源版没有。改用 Android 原生 `NotificationManager`，已实测跑通。

```ts
// Android 原生 API：NotificationManager / NotificationChannel / Notification.Builder
// 设备实测：Android 13(API 33)，context.getSystemService(NOTIFICATION_SERVICE) 可用，
//           NotificationManager.areNotificationsEnabled() 为 true，发通知无需再申请权限
var 通知ID = 1919
var 渠道ID = 'xjskp_result'

function 确保渠道(nm: any): void {
  // NotificationChannel 是 API 26+ 才有的类；低版本没有渠道概念，直接跳过
  if (device.sdkInt < 26) return
  var 渠道 = new android.app.NotificationChannel(渠道ID, '脚本执行结果',
    android.app.NotificationManager.IMPORTANCE_DEFAULT)
  nm.createNotificationChannel(渠道)   // 幂等，重复创建只更新名称/描述
}

function 发送通知(结果: '完成' | '已停止'): void {
  var 汇总 = 本轮汇总()
  var 标题 = 格式化通知标题(汇总, 结果)
  var 正文 = 格式化通知正文(汇总)
  var 明细 = 格式化通知明细(汇总)
  try {
    var nm = context.getSystemService(android.content.Context.NOTIFICATION_SERVICE)
    确保渠道(nm)
    // API 26+ 必须传渠道 id；低版本用无渠道构造函数
    var 构造器 = device.sdkInt >= 26
      ? new android.app.Notification.Builder(context, 渠道ID)
      : new android.app.Notification.Builder(context)
    构造器.setContentTitle(标题)
    构造器.setContentText(正文)
    if (明细) {
      // 对应原设计的 bigContent：通知下拉展开后的长文本
      构造器.setStyle(new android.app.Notification.BigTextStyle().bigText(明细))
    }
    // setSmallIcon 是必须的，缺了通知不会显示；借用系统自带的 info 图标
    构造器.setSmallIcon(android.R.drawable.ic_dialog_info)
    构造器.setAutoCancel(true)
    nm.notify(通知ID, 构造器.build())
    console.log('[通知] 已发送: ' + 标题)
  } catch (e: any) {
    console.log('[通知] 发送失败: ' + (e && e.message ? e.message : e))
    // 降级: 结果仍进日志与详细日志文件
    console.log(标题 + ' | ' + 正文)
    toast('通知发送失败，结果见运行日志')
  }
}
```

要点：

- **固定 id 1919 覆盖**：同 id 再次 `notify` 会替换上一条，通知栏不堆积。设备实测该 id 与 AutoX.js 自身的通知（`2147483647`、`2`）不冲突
- **可程序化断言**：`nm.getActiveNotifications()` 能列出当前活跃通知，测试里可硬断言通知真的发出去了——这是原 `notice` 方案给不了的能力
- **`setSmallIcon` 不能省**：缺小图标时 `notify()` 不报错但通知不显示，是这类改动最容易踩的坑
- **权限**：设备实测 `areNotificationsEnabled()` 为 true，不需要运行时申请。若为 false 则走 catch 降级分支

### 5. `src/model/daily.ts` — 埋点与生命周期

**删除** [daily.ts:62-65](../../../src/model/daily.ts#L62-L65) 的四个模块级计数器。总条数不再手工维护，而是"report 收到几个「任务结束」事件就是几条"——[daily.ts:522](../../../src/model/daily.ts#L522) 那种"总计 ≠ 三项之和"从结构上不再可能发生。

`doTask` 改造（新增可选第三参，默认 `true`；动作返回值放宽为联合类型，**原有的 `return false` 全部照常工作**）：

```ts
/** 任务动作返回值:true=成功;false=跳过(原因记为"未完成");对象=按 ok 判定并携带原因 */
type 动作返回 = boolean | { ok: boolean; 原因?: string }

function doTask(label: string, action: () => 动作返回, 配置?: { 计数?: boolean }): boolean {
  var 要计数 = !配置 || 配置.计数 !== false
  ...
  var r = action()
  var ok = typeof r === 'boolean' ? r : r.ok
  var 原因 = typeof r === 'boolean' ? '' : (r.原因 ? r.原因 : '')
  ...
  // 三态分支里原本的 successTasks++ / skipTasks++ / failTasks++ 全部换成:
  if (要计数) 发布({ 类型: '任务结束', 名: label, 状态: '跳过', 原因: 原因 ? 原因 : '未完成', 耗时: elapsed, 服: 服 })
  ...
}
```

`/计数: false` 时仍保留 try/catch 与全部日志，只是不发事件。

同步把 **33 处** `if (!nav(X)) return false` 改成 `if (!nav(X)) return { ok: false, 原因: '导航失败' }`——一条机械规则，`replace_all` 即可，现有 `return false` 的语义完全不变（`doTask` 仍判为跳过，只是原因从空变成「导航失败」）。

> **实现修订（2026-09-19，实现时实测）**：设计阶段写的"35 处"是数错了——`grep -c "if (!nav("` 得 36（33 个单行 + 3 个多行块），而 `grep -c ")) return false"` 得 35 是因为其中混进了 **2 处 `if (!ticketAction()) return false`**。按"只改导航失败"的规则，实际改 33 处；那 2 处 `ticketAction`（买票动作）失败保持普通 `return false`，原因记为「未完成」——"军团商店没券"与"进去了没事可做"目前是同一文案，细化留给将来在具体调用点用 `{ ok: false, 原因: '...' }` 显式提供。
>
> 另有两处计划未预见的**必要**改动（构建硬失败逼出）：一是 27 个内层动作函数签名的显式返回注解 `function (): boolean` 必须放宽成 `function (): 动作返回`，否则返回对象会报 `TS2322`；二是 `runDaily` 开头也有 4 行手写清零（`totalTasks = 0` 等）引用已删变量，必须一并删除，清零语义交给「本轮开始」事件。

**观影签到去重**（[daily.ts:407-424](../../../src/model/daily.ts#L407-L424)）：该条目的 `执行` 只是串接两个子 `doTask`（签到、便利店），自身无独立动作，却让 2 个开关被计成 3 条。规则是「**`doTask` 的 action 若只是串接其它 `doTask`、自身无独立动作，则不计数**」，故 [daily.ts:409](../../../src/model/daily.ts#L409) 传 `{ 计数: false }`，由两个子任务各自计数。

同一规则下 [daily.ts:279](../../../src/model/daily.ts#L279) 的 `军团` **保留计数**：它自己做了 `nav(军团)` 导航动作，且"军团页进不去"正是需要在通知里看到的异常。

`runDaily` 生命周期：

```ts
export function runDaily(): void {
  初始化通知(isDailyEnabled('执行结果通知'))   // 开关在此读一次
  发布({ 类型: '本轮开始' })
  var 正常结束 = false
  try {
    ...现有执行逻辑（含多服循环）不变...
    正常结束 = true
  } finally {
    发布({ 类型: '整轮结束', 结果: 正常结束 ? '完成' : '已停止' })
  }
}
```

`finally` 保证手动停止时也发通知。实测上能逃出 `runDaily` 的异常几乎只有 `isStopException`——其余异常都被 `doTask` 和 `nav` 接住了——所以「已停止」这个措辞是准确的。

**末尾的 console 摘要整段删除。** [daily.ts:518-523](../../../src/model/daily.ts#L518-L523) 依赖那四个被删掉的计数器，改由 `taskReport` 在收到「整轮结束」时输出——具体做法是新增一个纯函数 `格式化摘要(汇总, 结果): string`，订阅回调的「整轮结束」分支 `console.log` 它的返回值：

```
================================
   日常任务 — 完成
   成功: 12 | 跳过: 3 | 异常: 2 | 合计: 17
================================
```

文案里的「失败」一并改成「异常」，与计数条、通知栏用词统一。放 `taskReport` 而不是 `taskNotifier` 的原因：它是纯文本、不依赖 floaty，诊断脚本在无 UI 环境下也要能看到这段输出；而且详细日志开关会把它一起写进文件，正是需要留档的内容。

> **这条路径与通知开关无关，必须独立于 `taskNotifier` 存在。** 「执行结果通知」默认关闭，若摘要只在通知路径里输出，默认配置下跑完一轮日志里将没有任何汇总。因此 `taskReport` 必须自己处理「整轮结束」事件。
